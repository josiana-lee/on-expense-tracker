리뷰를 요청하면 코드를 고치지 말고 분류해서 보고만 한다.
"리뷰만 해줘"라고 명시하면 파일을 단 한 줄도 수정하지 않는다(에이전트 메모리는 예외).

**Why:** 사용자가 직접 판단하고 고치는 쪽을 선호한다. 출시 직전 시점에 에이전트가 임의로
건드리면 검증 범위가 다시 벌어진다.

**How to apply:**
- 분류 축은 상황에 따라 다르다. 평상시에는 심각도(CRITICAL/HIGH/MEDIUM/LOW/GOOD),
  **출시 임박 기능 리뷰에서는 "지금 고쳐야 / 다음에 같이 / 그냥 알아두면 될 것" 세 갈래**를
  직접 지정해서 요청했다. 요청에 축이 명시돼 있으면 그걸 그대로 쓴다.
- 항목마다 `파일:줄번호` + "이 코드에서 실제로 일어날 수 있는 일"을 붙인다. 원칙론 금지.
- 고치자는 제안에는 짧게라도 대안 코드를 붙인다.
- 레이아웃/폰트 관련 주장은 "넘칠 수 있다" 수준으로 두지 말고 실제 폰트 메트릭이나
  패딩 계산으로 수치를 제시한다. (fontTools로 advance를 재는 식의 검증을 환영했다.
  예: Pretendard 한글 advance는 0.8643em이라 Android 폴백(1.0em)과 4글자에 7.3px 차이)
- `pnpm typecheck` / `pnpm test` / `pnpm build`가 통과한다는 사실과, 변경된 코드에 실제
  테스트가 있는지는 구분해서 말한다. 확인 안 한 건 확인했다고 쓰지 않는다.
- 코드 주석의 **전제가 아직 유효한지**도 리뷰 대상이다. 이 프로젝트는 주석이 설계 문서라
  근거가 죽은 주석이 남으면 다음 사람이 잘못된 제약을 지키게 된다. 실제로 이 지점에서
  가장 좋은 지적이 나왔다.
- GOOD/유지할 판단은 굳이 필요 없다고 하면 빼도 된다 — 매번 넣지 말고 요청을 따른다.
