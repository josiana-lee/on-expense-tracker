## 30초 요약

안드로이드용 개인 지출 가계부. **서버가 없고 데이터가 기기 밖으로 나가지
않는다.** 회원가입도 로그인도 없다. React 19 + TypeScript로 만든 웹 앱을
Capacitor로 감싸 Play Store에 올렸고, 저장소는 IndexedDB(Dexie)다.

설계를 관통하는 원칙 하나: **"열자마자 3초 안에 지출 입력이 끝난다."**
이 문장이 아래 대부분의 결정을 설명한다.

## 왜 이 구조인가

### 서버를 두지 않았다

가계부는 **쓰는 사람 외에는 아무도 볼 이유가 없는 데이터**다. 서버를 두면
그 순간부터 계정, 인증, 유출 대응, 운영 비용이 따라붙는데, 이 앱이 서버로
얻는 건 기기 간 동기화 하나뿐이다. 개인 가계부에서 그 하나를 위해 나머지
전부를 감수할 이유가 없다고 봤다.

대신 **백업 파일이 데이터가 기기를 떠나는 유일한 통로**다. 사용자가 직접
파일로 뽑아 원하는 곳(드라이브, 메신저, 메일)에 두고, 새 기기에서 복원한다.
동기화를 사용자에게 넘긴 셈이고, 그 대가로 "우리가 가진 사용자 데이터"가
아예 존재하지 않는다.

### Capacitor를 골랐다 (PWA/TWA가 아니라)

처음엔 PWA로 올리는 안을 검토했다. 결정적인 차이는 **데이터 내구성**이었다.

브라우저나 TWA는 저장소를 브라우저가 관리해서, 용량이 부족하거나 사용자가
"사이트 데이터 삭제"를 누르면 **가계부 기록이 통째로 사라질 수 있다.**
네이티브 앱의 WebView 저장소는 앱에 귀속돼서 앱을 지우기 전엔 없어지지
않는다. 서버에 사본이 없는 앱이라 이 차이가 치명적이다.

부수적으로 공유 시트, 로컬 알림, 파일 접근 같은 네이티브 기능도 열렸다.

### 돈은 정수로만 다룬다

금액은 전부 **최소 단위 정수(`Minor`)**로 저장한다. 부동소수점을 쓰면
`0.1 + 0.2 !== 0.3` 같은 오차가 잔액에 쌓인다. 원화는 원이 최소 단위라
`toMinor`가 사실상 항등 함수인데, **그 사실이 실제로 버그를 낳았다**
(아래 "실패에서 배운 것" 참고).

### 삭제는 tombstone을 남긴다

레코드를 지울 때 삭제 기록을 따로 남긴다. 백업/복원에서 "이 기기에서 지웠다"
는 사실이 복원으로 되살아나지 않게 하기 위한 것이다.

## 기술 선택

| 선택 | 이유 |
|---|---|
| **React 19 + TypeScript** | 화면 23개, 상태가 화면마다 다름. 타입이 리팩터링의 안전망 |
| **Vite** | 빌드가 1초대. 반복이 빠른 게 개인 프로젝트에선 가장 큰 이점 |
| **Dexie (IndexedDB)** | localStorage는 동기·문자열·5MB 한계라 수천 건 기록엔 부적합. Dexie는 IndexedDB에 인덱스와 트랜잭션을 얹어줌 |
| **dexie-react-hooks (`useLiveQuery`)** | DB가 바뀌면 화면이 자동 갱신. 전역 상태 관리 라이브러리를 안 쓴 이유 — **DB 자체가 단일 진실 공급원** |
| **zod** | 백업 파일은 사용자가 고칠 수 있는 외부 입력. 런타임 검증이 필요한 유일한 지점 |
| **Capacitor** | 위 참고 |
| **CSS Modules** | 클래스 이름 충돌 없음. 런타임 비용 0. Tailwind를 안 쓴 건 이 앱의 스타일이 재사용보다 화면별 특수성이 큰 편이라 |
| **vitest + fake-indexeddb** | DB 로직을 브라우저 없이 테스트. 복원 같은 위험한 경로를 실제 트랜잭션으로 검증 |

**전역 상태 관리 라이브러리(Redux/Zustand 등)를 안 썼다.** 서버가 없어서
캐시 동기화 문제가 없고, `useLiveQuery`가 DB 변경을 구독하므로 화면 간
공유 상태가 사실상 없다. 넣었으면 DB와 스토어 두 개의 진실이 생겼을 것.

## 아키텍처

```
src/
  screens/      화면 (입력·달력·예산·자산·설정)
  components/   공용 UI (Sheet, Keypad, Toast, Icon …)
  hooks/        useLiveQuery 래퍼 (useCatalog, useExpenses …)
  db/           Dexie 스키마, 도메인 로직, 백업/복원
  lib/          순수 함수 (금액 포맷, 공유/다운로드, 플랫폼 판별)
  shell/        앱 셸, 뒤로가기 스택
```

원칙은 **"화면은 DB를 직접 만지지 않는다"**. 화면은 `hooks/`로 읽고
`db/`의 함수로 쓴다. 덕분에 도메인 로직이 React 없이 테스트된다 — 테스트
71개 중 대부분이 `db/`와 `lib/`을 대상으로 한다.

## 실패에서 배운 것

면접에서 가장 잘 먹히는 부분. 전부 실제로 겪은 일이다.

### 1. 브라우저에서 절대 재현되지 않는 버그

**증상** 실기기에서 목록이 스크롤되지 않고 하단 탭 막대가 사라졌다.
드래그하면 한 번 울렁이고 멈췄다. 브라우저에서는 완벽했다.

**원인** 앱 전체 높이를 `height: 100dvh`로 잡았는데, `dvh` 단위는
Chrome/WebView 108(2022-12) 이상에만 있다. 그보다 낮은 안드로이드 System
WebView는 **선언을 통째로 버린다.** 높이가 `auto`가 되면서 요소가 내용만큼
늘어나고, `overflow: hidden`이 아래를 잘라내 탭 막대가 화면 밖으로 나갔다.
동시에 안쪽 스크롤 영역이 "넘칠 게 없다"고 계산해 스크롤이 죽었다.

**해결** 폴백을 먼저 선언한다. 이해하는 브라우저는 뒤를 쓰고, 못 하는
WebView는 앞을 쓴다.
```css
height: 100%;      /* 폴백 */
height: 100dvh;
```

**배운 것** 두 가지다. ①**"최신 문법"의 기준은 내 브라우저가 아니라 가장
낮은 기기다.** 같은 이유로 `color-mix()`(WebView 111)도 폴백을 넣었다.
②**미니파이어가 "중복"이라며 폴백을 지우면 수정이 무의미해진다** — 빌드
결과물과 AAB 안의 CSS까지 열어 확인했다.

### 2. 없는 API를 있다고 가정한 것

**증상** 복원 직전에 자동으로 만드는 안전 백업이 실기기에서 항상 실패로
판정됐다. 그래서 복원이 아예 진행되지 않았다.

**원인** `navigator.canShare`로 공유 가능 여부를 확인했는데, **이 API는
안드로이드 WebView에 없다.** 웹 표준 문서에는 있지만 WebView에는 구현이
없어서 항상 `undefined`였다.

**해결** 성공/실패 불리언을 버리고 3상태로 바꿨다.
```ts
type HandoffResult = 'shared' | 'downloaded' | 'cancelled';
```
불리언이 **"사용자가 거절함"과 "다른 경로로 성공함"을 같은 값으로 뭉갠 것**이
근본 원인이었다. 상태를 나누자 "저장 안 했으면 복원을 멈춘다"는 판단이
정확해졌다.

**배운 것** 타입이 부족하면 로직이 거짓말한다. 불리언으로 표현할 수 없는
결과를 불리언에 욱여넣는 순간 버그가 예약된다.

### 3. 서비스 워커가 이전 버전을 계속 서빙한 것

**증상** 안드로이드 뒤로가기 버튼이 아무 반응이 없었다. 네이티브 코드에는
분명히 핸들러가 있었다.

**원인** PWA로 만들 때 붙인 서비스 워커가 남아 있었다. WebView 저장소는
앱을 업데이트해도 유지되므로, **이전 릴리스의 워커가 이전 번들을 계속
내주고 있었다.** 새 네이티브 코드 옆에 리스너가 없는 옛 JS가 붙어 있던 것.

**해결** 빌드에서 자기파괴(self-destroying) 워커를 내보내고, 앱 부팅 시에도
남은 등록을 해제한다. 이미 설치된 기기의 워커는 **같은 URL에 자기파괴 워커를
내려주는 것 말고는 없앨 방법이 없다.**

**배운 것** 하이브리드 앱에서 웹 레이어의 캐시는 네이티브 업데이트와 수명이
다르다. 두 레이어의 생명주기가 어긋나는 지점을 의심해야 한다.

### 4. 스케줄 기능을 만들었다가 걷어낸 것

반복 지출을 처음엔 "매월 25일에 자동 기록" 방식으로 만들었다. 쓰다 보니
**월세는 날짜가 정해져 있어도 실제로는 하루 이틀 앞뒤로 낸다.** 자동으로
잘못된 날짜에 꽂힌 기록은 사용자가 찾아가서 고쳐야 하는데, 그건 처음부터
직접 입력하는 것보다 더 큰 일이다.

**결론: 잘못된 기록이 빠진 기록보다 비싸다.** 스케줄을 전부 걷어내고
"이름 + 금액 + 카테고리 + 결제수단을 저장해두고 탭 한 번으로 채우는
템플릿"으로 바꿨다. 자동 기록은 없고, 저장은 언제나 사용자가 누른다.

**배운 것** 기능을 지우는 것도 설계다. 그리고 이 판단이 이후 결정의 기준이
됐다 — 입력 화면 칩도 "누르면 채워질 뿐, 저장은 여전히 사용자가" 로 만들었다.

### 5. 테스트가 없었으면 조용히 나갔을 버그

스케줄을 걷어내며 함수를 다시 쓸 때, 저장된 금액을 100으로 나눠서 넘기는
코드를 넣었다. **원화는 `toMinor`가 항등 함수**(원이 최소 단위)라 나눌 게
없는데도. 60만원 템플릿을 누르면 **6천원이 기록됐다.**

화면 어디에도 오류가 없다. 금액만 조용히 틀린다. 새로 쓴 테스트가 첫 실행에서
이걸 잡았다.

**배운 것** "순수 함수를 고쳤는데 테스트를 안 쓰면, 통과는 그 변경에 대한
증거가 아니라 **그 변경을 건드리지 않은 코드에 대한 증거**일 뿐이다."
이후 위험한 수정에는 **변이 테스트**를 붙였다 — 고친 부분을 일부러 되돌려서
해당 테스트가 실제로 실패하는지 확인한다. 통과만 보고 넘어가면 아무것도
검증하지 않는 테스트를 가진 줄도 모른다.

## 품질을 어떻게 보장했나

- **테스트 71개**, 대상은 DB 로직과 순수 함수. `fake-indexeddb`로 실제
  트랜잭션까지 검증한다. 복원처럼 되돌릴 수 없는 경로에 집중했다.
- **변이 테스트.** 중요한 수정마다 고친 곳을 되돌려 해당 테스트가 실패하는지
  확인한다. 테스트가 진짜 그 동작을 잡고 있는지 확인하는 유일한 방법.
- **타입 레벨 불변식.** 런타임 검사로 잡을 수 없는 것을 컴파일 타임으로
  올렸다. 백업 스키마가 타입 정의보다 뒤처지면 `typecheck`가 깨지고,
  버전 번호 세 곳이 어긋나도 테스트가 깨진다.
- **실제로 눌러본다.** 타입체크 통과는 동작의 증거가 아니다. 기능마다
  브라우저에서 실제 IndexedDB 상태를 열어 확인했고, 실기기·에뮬레이터에서
  다시 확인했다.

## 출시 과정에서 배운 것

- **내부 테스트와 비공개 테스트는 다르다.** 2023-11-13 이후 만든 개인
  개발자 계정은 **비공개 테스트에서 12명이 14일 연속 참여**해야 프로덕션
  액세스를 신청할 수 있다. 내부 테스트는 이 요건에 포함되지 않는다.
- **versionCode와 versionName은 다른 것.** 앞은 Play가 순서를 매기는
  정수(사용자에게 안 보임), 뒤는 사용자가 보는 이름. 정식 출시 전까지
  versionName은 `1.0.0`으로 두고 versionCode만 올린다.
- **에뮬레이터는 실기기가 아니다.** 위 1번 버그는 브라우저에서 안 나오고,
  공유 시트 관련 문제는 공유 대상이 없는 에뮬레이터에서 끝까지 볼 수 없다.

## 지금 아는 걸로 다시 한다면

- **가장 낮은 기기 기준을 처음에 정한다.** 최소 지원 WebView 버전을 먼저
  못 박았으면 `dvh`/`color-mix` 문제를 애초에 안 만들었다.
- **네이티브 판별을 더 일찍 넣는다.** 개발용 화면 틀이 실기기까지 따라
  나가서 펼친 폴더블에서 앱이 화면 가운데 카드처럼 떴다. CSS에는 "데스크톱
  브라우저"를 판별할 수단이 없는데 화면 폭으로 대신하고 있었다.
- **스케줄 기능은 만들기 전에 내 사용 패턴을 먼저 적어봤어야 했다.** 만들고
  나서야 "실제로는 날짜가 안 맞는다"를 알았다.
